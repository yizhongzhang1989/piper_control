## 真机调试发现与修复

设备为 `arm_2 / can1`，采用原重力和摩擦标定。测试只通过通用接口规划小幅运动，
指令速度上限设置为 0.08 rad/s。早期运行完成过 movej、关节轨迹、movel、movec、
关节/TCP/Twist 实时流、超时及取消；随后更严格的复验发现终点偏差与退出问题。
已有失败结果保留于 [硬件记录](hardware-acceptance.json)。

原柔顺增益下 J4 有约 0.025 rad 静态误差。独立位置控制 profile 调整 J1/J4
增益后，曾完整完成一次 0.01 rad 终点容差验收；但实测短时速度高于指令上限，
并在继续复验时观察到异常固件模式与未预期姿态变化。因此这次成功不作为最终
合格依据。指令限速不能保证真实关节速度绝不超过该数值。

最初的 API 退出实现先切固件关节模式再发送当前位置，存在旧目标被采用的风险。
该实现已移除。现在保持 MIT 模式：未修改的驱动由独立 ROS 固定目标进程接管，
带补丁的驱动自行保留超时目标；API 在接管确认前继续发布，不终止底层驱动。
真实的 API→保持进程→API 交回保留了相同目标，前后最大关节变化 0.00063 rad：
[接管记录](hold-handoff-verification.json)。这验证发布接管，不等于固件当前就绪。

## 当前阻塞

原始 `0x2A1` 状态持续在 `ctrl_mode=2`、`teach_status=1/2` 间切换；总线上没有
观察到开始示教指令。结束示教、Follower 配置及终止执行探测没有恢复稳定控制。
上游 `mit_ready` 可能保留旧值，所以新适配层直接检查原始状态，要求连续 100 ms
确认 CAN/MIT 模式，才置 `command_ready=true`。当前不满足，新运动会被拒绝。

用户已确认实体按钮松开、没有卡住。原驱动暂停 0.4 s、以相同六帧 MIT 支撑和
10 Hz 模式请求隔离重试期间，固件仍处于示教状态，且未观察到关节移动。
因此不能把原驱动的结束示教重试循环认定为唯一根因。vendor 已修复独立确认的
旧 `mit_ready` 标志问题，原工作空间与运行驱动没有替换。

随后一次 SDK `reset()` 探测发生了延迟重初始化和实际移动，用户确认当前稳定、
没有碰撞。这次风险判断不充分。进一步查到[厂商明确说明](https://github.com/agilexrobotics/piper_sdk/issues/66#issuecomment-3162642963)
该指令会关闭电机，持续 MIT 支撑不能消除这一行为。不能把复位瞬间的零反馈当成
真实运动量，也不能将短时隔离期间的零运动当作整个复位安全的证据。

之后两轮独立关节使能仍未恢复控制权。[完整摘要](hardware-recovery-2026-11-26.json)
保留前后状态、指令、首个异常与现场确认。当前原驱动继续固定目标输出，不推进
轨迹；继续需要掉电的厂商恢复流程前，等待用户提供可靠物理支撑。

恢复 `command_ready=true` 后，需低速返回[初始被动 CAN 记录](hardware-initial-passive.json)
中的 `positions` 姿态，重跑完整硬件验收、
标准 ROS action 和退出/重连接管验证，再更新本记录为最终结论。
